## Implemented compatibility rules

- Config validates target/environment/host. PdoFactory fetches actual VERSION() and @@version_comment; DatabasePlatform validates family and version before caching. Target/engine mismatches and wrong versions fail; MariaDB's optional 5.5.5 prefix is recognized. This is explicit support, not removal of the version guard.
- Require InnoDB, native PDO prepares, UTC sessions, strict SQL including ONLY_FULL_GROUP_BY, enabled FK checks and MariaDB CHECK checks. Connection setup restores required settings. Stock transactions remain caller-owned, using primary-key FOR UPDATE and atomic movement/audit/idempotency effects, with no quantity triggers.
- Explicit shared utf8mb4_unicode_ci for human text/category uniqueness; ascii_bin for normalized SKU, operation keys, roles and movement-type tokens; utf8mb4_bin for JSON text. Role/type checks must remain case-sensitive. Category uniqueness has case/accent and trailing-space comparison semantics. Binary VARCHAR still has padding semantics: application validation must normalize/reject identifier whitespace. Avoid MySQL-only utf8mb4_0900_*.
- Portable JSON uses explicit LONGTEXT utf8mb4_bin plus a full named CHECK (payload IS NULL OR JSON_VALID(payload)), generated by DatabasePlatform::jsonColumn. Avoid native JSON equality, JSON defaults and MySQL-only operators. CanonicalJson recursively sorts object keys, preserves list ordering and rejects floats/objects/resources; decimal values are strings. Future validation must enforce structure/bounds and reject duplicate JSON keys before canonical encoding. MariaDB's [JSON alias](https://mariadb.com/docs/server/reference/data-types/string-data-types/json) differs from MySQL's native representation.
- Use full named FOREIGN KEY (...) REFERENCES ... ON DELETE RESTRICT, positive movement quantities, nonnegative balances/prices and exact role/type checks. MariaDB 10.4 ignores column-only REFERENCES shorthand; see [CREATE TABLE](https://mariadb.com/docs/server/reference/sql-statements/data-definition/create-table). UNIQUE permits multiple NULL correction links but rejects duplicate non-NULL links. Actual domain correction self-reference and constraints passed Stage 4; reversal/stock/application behavior passed Stages 8–12 locally.
- DatabasePlatform classifies native duplicate/FK/CHECK/deadlock/lock-timeout/range errors internally. MariaDB CHECK 4025 and MySQL CHECK 3819 map consistently; future service translation retains API contracts and sanitized envelopes. Deadlock classification is code, not an actual deadlock-test pass. No authorization, HTTP routes, role response fields or API contract changed.
- Future migrations require checksummed portable DDL, explicit engines/collations/constraints and engine-aware introspection. DDL commits implicitly; never assume transactional DDL rollback. Fresh/rerun/upgrade, reconciliation, EXPLAIN, backup/restore and full domain races must run independently on each actual target.

## Actual local verification and setup adjustment

Used installed C:/xampp/mysql/bin/mysqld.exe; SELECT VERSION() returned 10.4.32-MariaDB and @@version_comment returned mariadb.org binary distribution. Provisioned separate ignored .tools/mariadb/data, loopback port 13307, private random credentials and empty bizstock_local. Existing XAMPP data/configuration and Windows services were untouched. Development account has DDL rights only on that local database; production needs separate migration/runtime privileges.

The initial native asynchronous-I/O instance hung during repeated CREATE TABLE. InnoDB status showed pending native writes/latch waits. Its forced stop left disposable system-table damage; that directory was preserved as .tools/mariadb/failed-native-aio-data and a new empty workspace instance initialized. Local configuration now uses innodb-use-native-aio=0, a [documented I/O setting](https://mariadb.com/docs/server/server-usage/storage-engines/innodb/innodb-system-variables). This workaround is inferred from the observed hang, not a claim that every XAMPP installation needs it. Durability, InnoDB and constraints remain enabled. Never apply that disposable-instance recovery procedure to an existing business database.

The suite verifies native prepares, UTC/strict modes, InnoDB, Unicode/case/space uniqueness, exact roles/types, JSON/DECIMAL/microsecond round trips, invalid JSON/roles/types/quantities/prices/overflow rejection, FK RESTRICT, actor-scoped uniqueness, NULL/non-NULL correction uniqueness, prepared-value injection resistance, rollback, stale conditional update, independent-process FOR UPDATE blocking and rejection of a competing OUT after committed balance, plus lock timeout/rollback. Probe tables are removed; no domain schema/migrations applied.

Run composer check:database for connection/session policy and composer test:database for disposable capability probes on the configured local/test database. Probes need CREATE/DROP and touch only random compat_<hex>_* tables; never use production. See [setup](../README.md). Actual application oversell/reversal/archive/last-Admin races, authentication/authorization/CSRF, deadlocks, migration upgrade and production MySQL evidence remain pending for their owning stages.

Stages 8–12 add no migration or engine-specific schema change. Actor/product locking, actual deadlock/timeout retries, durable JSON replay, opening stock, reversal/archive races, read-only snapshots, exact decimal totals and CSV/report date behavior now pass on this local MariaDB target. The matching MySQL 8.4 test commands are ready but have not run against MySQL. Do not infer MySQL acceptance, production HTTPS acceptance or production suitability of MariaDB 10.4 from these local passes.
