# Stage 6 authentication

Implemented: GET /api/v1/auth/csrf, POST /auth/login, POST /auth/logout, GET /auth/me and PATCH /account/password (all under /api/v1). The real /login and /account screens use shared components and the browser API client. Root links to them. Local /preview screens remain explicitly isolated fixtures; they do not authenticate.

Fetch the CSRF bootstrap before login; send X-CSRF-Token on every mutation, including login and logout. CSRF is session-bound, constant-time compared, and rotated with the session ID after login/password changes. Logout permits an empty body or an empty JSON object, destroys the server session and expires its cookie. No public signup, JWT, CORS allowance or browser storage of credentials/tokens. Identity responses use a positive field projection and never contain hashes or session_version. UTC timestamps retain microseconds.

Usernames are ASCII, trimmed/lowercased and bounded to 50 characters. Invalid username/password, missing user and inactive account return the same 401 INVALID_CREDENTIALS. Supplied passwords are never trimmed. New passwords reuse PasswordPolicy: valid UTF-8, 12–72 bytes, no NUL or all-whitespace input; current password required and replacement must differ. PHP PASSWORD_DEFAULT hashes and password_verify implement credential checks. Password change locks/rechecks the user and atomically updates hash, version, forced-change flag and a metadata-only audit. An audit failure rolls back the change. The current session rotates and retains its original absolute deadline; all other sessions fail their next protected request.

Private PHP file sessions live in var/sessions/<environment/database/base-path SHA-256>/ outside public/. Use private filesystem ownership/ACLs; one local filesystem is suitable for this single-node application. Multi-node hosting requires deliberate shared session storage, not uncoordinated node-local files. PHP strict mode, cookie-only IDs, no URL rewriting, HttpOnly, SameSite=Lax and base-scoped session cookies are enforced. Production additionally requires direct HTTPS and Secure; untrusted forwarded-protocol headers are ignored. TLS/proxy/hosting integration remains Stage 15 verification. Only local/test may use HTTP cookies. Every response is no-store; account names and metadata are HTML escaped and scripts use textContent.

SESSION_IDLE_SECONDS defaults to 1800 (30 minutes); SESSION_ABSOLUTE_SECONDS to 28800 (8 hours). Inactivity or absolute deadline expires access at the boundary. Protected requests refresh idle time, never the absolute deadline. Config requires idle 300–86400 seconds in local/production (test minimum 1), absolute >= idle and <=604800. Session file garbage collection is housekeeping, not the security expiry mechanism. Current active status, role and session_version are read from MariaDB on every protected request; do not trust role flags in the browser or session.

Database-backed fixed-window throttles consume every syntactically valid, CSRF-valid login attempt (including successes): 5 per normalized account and 30 per REMOTE_ADDR in 5 minutes. Password changes have independent account/peer buckets with the same bounds. Hash keys contain no plaintext username/IP/password. Bucket insert/lock/reset/increment happens in a transaction with consistent peer-before-account locking; blocked peers cannot create extra account buckets. Limits survive workers/restarts and return 429 with Retry-After. A client cannot evade peer limits through X-Forwarded-For. Invalid CSRF does not consume credential attempts. Account-wide throttling trades availability under deliberate lockout attacks for bounded guessing; production monitoring/recovery is later operational work.

Forced-change accounts can only change their own password or log out; necessary CSRF bootstrap and the protected account page remain available. /auth/me and all business APIs return PASSWORD_CHANGE_REQUIRED until changed. Initial owner/development credentials require this flow. Admin reset/emergency recovery and last-Admin management remain Stage 13, not implemented by this stage.

Reusable authorization gates cover every planned business operation with the requirements matrix. Viewer cannot access suppliers/history/reports/users/audit or any business write; Staff cannot manage metadata/lookups/users or reverse movements. Viewer price sorting and supplier filtering fail with generic 403. Positive product/category serializers exclude hidden fields and nested extras. Stage 7 category/supplier handlers are now real; remaining business handlers are planned, returning 404 for authorized requests and 401/403 for denied requests, never simulated success. Later feature stages must use these policies and test real response/query parity.

Verification: composer test:auth creates a uniquely named disposable database on the configured loopback engine, migrates it, runs actual HTTP/API and installed Chrome checks, then drops only its own database and sessions. Private test administrator credentials are inherited from the isolated MariaDB configuration or TEST_DB_ADMIN_USER/TEST_DB_ADMIN_PASSWORD. Tests do not alter installed users, development credential files or stock. MariaDB 10.4.32 local passed independently; MySQL 8.4 and production TLS/host verification remain pending.
