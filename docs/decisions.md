## Usability follow-up (2026-10-12)

Aggregate the complete ledger in one read snapshot over 7/30 Manila calendar days including today: convert midnight boundaries to UTC and group at +08:00, zero-fill days, retain exact SQL decimal-string totals. ## Stage 7 decisions

- Reuse existing lookup tables/unique category names/RESTRICT product references unchanged. Admin mutations reread active role/session version under a user lock, lock existing parent rows and atomically audit. Foreign keys backstop concurrent referencing product creation; never cascade/reassign automatically or modify stock/history.
- Literal name-only substring search escapes SQL LIKE wildcards, uses native parameters and bounded shared pagination; allowed sorts ID/name with ID tie-break. Category uniqueness remains case/accent insensitive under utf8mb4_unicode_ci. No cross-request search snapshot is promised.
- PATCH is partial and requires at least one field; omitted supplier email retains it, null/blank clears it. Conventional email <=100 characters; category/supplier names <=100/150. Duplicate/reference conflicts are safe typed 409s; missing records 404. DELETE accepts empty body or empty object. Failed domain/audit mutations roll back together.
- Shared read-only screens omit Admin controls and Viewer supplier navigation on the server; APIs independently enforce policy. Native confirmation, safe textContent, loading/empty/error/retry, stale-fetch cancellation, search/sort and pagination use existing components/client. No write auto-retry or idempotency promise. MySQL 8.4 and production HTTPS stay pending; remaining stages are unchanged.

## Stage 6 decisions

- Reuse existing users/session_version/must_change_password, rate_limits and audit_events; no new or modified migrations. PDO repository reads/writes are prepared; services own rate-limit and password/audit transactions. Password changes invalidate other sessions and retain the current session's original absolute deadline.
- Private cookie-only strict PHP file sessions use a per-environment/database/base-path directory; default idle/absolute lifetimes 30 minutes/8 hours. Production requires direct HTTPS and Secure/HttpOnly/SameSite=Lax. Local/test HTTP is explicit; proxy trust/shared multi-node storage awaits hosting decisions.
- Persistent independent login and password-change buckets allow 5 attempts/account and 30/peer per 5 minutes, counting successes too. Use REMOTE_ADDR, never forwarded client identity. Lock peer before account consistently; blocked peers cannot create more account buckets. Generic errors and a timing-only hash conceal unknown/inactive accounts; no secret logging/storage in the browser.
- Forced-change sessions allow password change/logout, required CSRF bootstrap and the account page; me/business access stays restricted. Initial owner/development passwords work through real /login, not fixture previews. Admin reset/recovery remains Stage 13.
- Install security gates ahead of all planned business handlers and positive user/product/category serializers now. Allowed business requests remain 404, denied requests 401/403. Feature stages must test actual returned data/filter parity; Stage 6 does not claim those handlers exist. MariaDB local acceptance and production cookie configuration are verified; actual MySQL and production TLS remain pending.

## Stage 2 runtime and implementation decisions

- Select PHP 8.5.x and MySQL 8.4.x LTS. PHP 8.5.11 portable x64 NTS is verified locally using the official ZIP and SHA-256 from [PHP downloads](https://www.php.net/downloads.php?os=windows); [support policy](https://www.php.net/supported-versions.php) lists the supported branch. Apache-module use requires TS or a configured FastCGI runtime; the existing XAMPP PHP was not replaced.
- System tools detected: PHP 8.2.12, Composer 2.9.8, Apache 2.4.58 and MariaDB 10.4.32 client. No responding database server. MariaDB is not silently accepted as [MySQL 8.4 LTS](https://dev.mysql.com/doc/refman/8.4/en/mysql-releases.html). Target database and actual host compatibility remain unverified prerequisites for later database/deployment stages.
- Composer PSR-4 autoloads BizStock\\ from src/. Seven packages are locked; phpdotenv 5.7.0 loads configuration and Bootstrap 5.3.8 supplies pinned local assets. Manifest uses compatible constraints, while composer.lock fixes exact installed versions; asset hashes require deliberate coordinated update. Scripts provide setup/assets/serve/lint/test/runtime/database checks; no extra test framework needed for this foundation.
- / and /api/v1/health are the only implemented application routes. Health is liveness only, does not connect to DB or claim readiness. API foundation/OpenAPI remain Stage 5. Unknown routes fail 404, known routes reject non-GET/HEAD with 405; HEAD omits body.
- Central Config validates base path and DSN fields, keeps PHP/Manila business settings with UTC runtime, honors process environment before ignored .env, and prohibits public log storage. Errors are sanitized in every environment; internal logs record request ID/class/file/line without raw messages or arguments.
- PdoFactory is lazy/shared per factory, native prepared statements, utf8mb4, strict SQL mode, UTC connection and explicit target-version enforcement. Its actual MySQL connection has not been verified. No business SQL or migrations introduced.
- Git initialized for the Stage 2 repository. No commit made; secrets/runtime/vendor/generated assets ignored. Elevated Composer reported ownership warning because sandbox/elevated users differ; dependency install succeeded and normal workspace Git operations pass. No global safe.directory setting was changed.

## Stage 4 decisions

- Ten tables implement the five domain tables plus operation_requests, audit_events, schema_migrations, rate_limits and security_locks. Immutable ordered SQL is tracked by SHA-256 with an advisory migration lock and running/applied state plus completed statement count. Incomplete DDL blocks rerun for explicit review; no reset command or automatic history rewrite. An unmanaged baseline is refused without changing its existing records.
- Separate core, supporting-table and access-index migrations permit a real additive upgrade rehearsal against existing account/product/movement data. Portable text JSON, named RESTRICT FKs and binary role/type/identifier checks implement the compatibility policy; checks avoid AUTO_INCREMENT/FK-action columns. Concrete types/indexes are in schema.md. MySQL 8.4 is reviewed as the intended target but actual execution remains pending.
- Initial Admin provisioning is CLI-only, stdin secret input (hidden double prompt on Windows), 12–72-byte UTF-8 password hashing with PASSWORD_DEFAULT, security-sentinel lock, empty accounts requirement, forced change and atomic safe audit. No password/default credential is embedded, printed or reset on rerun. This is not Stage 13 emergency recovery.
- Development fixtures require local/test plus loopback and empty domain/support data. Independently random credentials are stored outside public/ in ignored var/development-credentials.json before committing; failed credential delivery rolls back seeds. A safe audit marker makes reruns no-ops. This Stage 4 fixture-only transaction creates zero products, consistent opening/OUT movements and matching balances/replay rows; replace that insertion sequence with the shared StockMovementService in Stage 8. No business writer is exposed now.
- Read-only snapshot reconciliation is implemented early to satisfy Stage 4 seed acceptance and reused by Stage 8: every product, archived/no-movement included, wide decimal movement sums, nonzero drift exit and no repair. MariaDB tests passed independently; later auth/business integrity races and all MySQL proof remain pending.

## Stage 13-15 implementation decisions

Use the existing singleton security lock before actor/target account locks for concurrent last-Admin protection. Every account change revokes sessions through session_version; resets/recovery require a fresh forced password change, and secret values never enter audit projections. Emergency recovery uses trusted local CLI stdin and a required reason.

Keep native database backup/restore separate from HTTP and require an empty restore target; never erase an occupied database. Use distinct runtime and administrative principals, preserving append-only history/audit privileges. A manual self-hosted CI workflow is authored but execution remains pending. MariaDB 10.4.32 remains local-only; no production compatibility or participant feedback is inferred from local tests.
